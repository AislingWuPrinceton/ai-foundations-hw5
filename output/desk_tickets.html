1. How the agents performed on each ticket

Ticket 101: Bulldog tee

What worked.

  • Observed Closed with every cash amount correct. The ticket ended closed after the human approved invoice payment #1 ($840, payment 1) and restock purchase #2 ($8, PO 1). Both amounts were computed by the server from invoices.amount and pricing.unit_cost, and checking moved exactly $3,400 → $2,560 (Cash tab).
  • Observed Nothing was prepared twice. Run 2 read the "actions already on this ticket" context, saw #1 executed, and did not prepare another invoice payment. Run 3 saw #2 executed and prepared no duplicate purchase.
  • Observed The blocking invoice was found and used. Inventory found that Bulldog Print Co was blocked by open invoice 501 (list_vendors), and Accounting turned that into a single payment action.
  • Observed No errors. There were no tool errors, guardrail blocks, or retries in the three runs.

What did not work as well.

  • Observed Three runs and two approval rounds. In run 1, Inventory reported that "a restock cannot be prepared until that invoice is paid" and did not call prepare_purchase. The purchase was only prepared in run 2. That cost a second approval round and a run of 9 requests and 29,186 tokens. Inferred The approval step would have refused the purchase only until #1 executed. So preparing both actions in run 1 might have saved one run, if the human approved them in order.
  • Observed The same lookup ran seven times. check_stock_and_pricing for the same SKU and size was called 7 times across 3 runs, by Inventory, Accounting, and Customer Service. Customer Service was not expected to look anything up.
  • Gap Possibly a duplicate order. Invoice 501's description is "Rush reprint CC-TEE-WHITE S". If that reprint was already the restock, PO 1 may duplicate it. No field links the two, and no agent questioned it.
  • Observed The tee is still out of stock. The ticket is "resolved" under the owner's closing rule, but inventory still shows 0 size-S tees. The run-1 reply draft also told the customer the tee "has not been ordered", which was true at that moment but was superseded later.
  • Observed Privacy gap. The reply drafts greeted the customer by first name, and that first name reached the audit trail because the redactor only matched the full name. This was fixed after the run; earlier entries were not rewritten.

Consequences of the differences.

  • Observed Approval moved out of the run. Approval now happens on the dashboard between runs instead of inside one. So every ticket needed a follow-up run after approval before it could close: 2 runs for 102 and 103, and 3 for 101. The Expected Branch A for 102 had predicted closing in the same run.
  • Observed Running 101 first changed the other two tickets. The Expected plan for 103 predicted that the vendor would still be blocked. Because 101 was run first and invoice 501 was paid, Inventory found the vendor unblocked and prepared the purchase immediately. The predicted 102 balance of $3,400 → $1,000 became $2,560 → $160, because the $840 had already been paid.
  • Observed Restocking became possible. The plan said restocking needs a human because "there is no ordering tool". With prepare_purchase, the team itself prepared orders for 101 and 103. That added a second approval to 101 and the $8 and $264 purchase orders on the Cash tab.
  • Observed Extra lookups instead of passed findings. The plans assumed Accounting and Customer Service would reuse findings passed to them; in practice they repeated lookups: the same stock or lease lookup ran 7 times for 101, 4 times for 102, and 6 times for 103. Nothing about the result was wrong, but it added tool calls.
  • Inferred Why Boss delegated to Accounting itself. The audit trail records no reason for Boss sending work to Accounting itself instead of letting Inventory or Facilities hand it on. One possible explanation: Boss's prompt tells it to "delegate each fact-finding job to the right specialist" and read each report before deciding the next step, while the specialists' prompts allow delegation only "when you truly need" another role.
  • Inferred Why 103 never used the 0% baseline. The owner's 10% decision was supplied up front, so the 0% baseline the plan predicted (for a run with no decision) had no purpose.

3. What would have been simpler with one agent using tools

Observed In all seven runs, Boss made every one of the 16 delegations. No specialist delegated to another. Each delegation started a new agent loop that received the ticket context again and returned a report that Boss then read. Input tokens were 216,900 of 237,637 (91%).

  • Ticket 102 Observed: the work was one lease lookup, one prepare_payment, and one status update, but it went Boss → Facilities → report → Boss → Accounting → report → Boss in each run, and get_rent_due_and_cash ran twice per run. One agent holding get_rent_due_and_cash, prepare_payment, and update_ticket_status could do the same three steps with no delegation and no repeated lookup.
  • Repeated stock checks on 101 and 103 Observed: check_stock_and_pricing ran 13 times across those tickets because Inventory, Accounting, and Customer Service each looked up the same SKU. A single agent would call it once per run.
  • Re-checking a pending action Observed: the retry in 103 came from Accounting filing a report that Boss then had to combine. One agent would file one report per run.
  • Inferred How much it would save. A single agent would likely need fewer requests and tokens. That was not measured, so no saving is claimed here.

Tradeoffs that would remain.

  • Least privilege would be lost. Today each role sees only its own tools: Facilities has one MCP tool, and only Accounting can prepare payments. One agent would hold all of them, including both prepare tools and update_ticket_status.
  • Customer names would be harder to contain. Inventory and Accounting currently see the requester as "[redacted]" on 101 and 103; one agent would see the name throughout.
  • The reply guard would need a new home. The rule that rejects reply drafts mentioning cost, margin, or invoices currently attaches to the customer-facing report; it would have to apply to one mixed report instead.
  • Responsibility would be less visible. The audit trail and dashboard panels attribute each tool call to a role (for example, "prepared by inventory" on PO 1 and PO 2); with one agent that breakdown disappears.
  • What would not change. The human approval route, the server-side amount checks, the no-negative-cash rule, and the close guard are enforced outside the agents, so they would stay the same either way.

4. Three new problems the current team could solve Hypothetical

Each scenario needs a new row in tickets. No MCP tool or route creates tickets, so a person or another system would have to add it. Everything after that uses only tools that already exist.

S1 · Bulk quote for Yale Caps

Problem: a student group asks for a price on 30 Yale Caps (CC-HAT-BLUE, size OS) with a bulk discount.

Agents: Boss, Inventory, Accounting, Customer Service.

MCP tools: get_ticket, check_stock_and_pricing (40 on hand, so no shortfall), quote_bulk_discount (cost $6, list $22), update_ticket_status.

Data needed: the ticket row (sku, size, qty), inventory, pricing.

Human input: the discount percentage, entered as a decision in the dashboard note, because there is no discount policy. No approval route is needed, since no money moves and nothing is ordered.

S2 · Restock the Crest Mug

Problem: a customer orders Crest Mugs (CC-MUG-CREST, OS), which show 0 on hand.

Agents: Boss, Inventory, Customer Service.

MCP tools: check_stock_and_pricing, list_vendors (Elm City Gifts, "mugs and small goods", 3 lead days, no open invoices), prepare_purchase (qty × $3.50), update_ticket_status.

Data needed: the ticket row, inventory, pricing, vendors, invoices.

Human approval: yes, the purchase on the dashboard. It records an order only.

S3 · Pay a new vendor invoice

Problem: a new open invoice from QuickShip CT (vendor 3) is linked to a ticket.

Agents: Boss, Accounting.

MCP tools: get_invoice_with_vendor, get_cash_balances, prepare_payment (invoice_payment), update_ticket_status.

Data needed: the invoice row (amount, due date, vendor 3) and the ticket row with its invoice_id.

Human approval: yes, the payment. With checking at $160, the approval would be refused unless the invoice is $160 or less.

5. Three new problems the current implementation could not fully solve Hypothetical

S4 · The ordered stock arrives

Problem: the goods for PO 1 (1 tee) and PO 2 (12 hoodies) arrive.

Gap: no tool adds received goods to inventory.qty, marks a purchase order received, or records the vendor's bill. Inventory would keep showing 0 tees and 8 hoodies.

Needed:

  • a receiving tool that updates inventory and purchase_orders.status in one transaction;
  • a way to create the matching vendor invoice;
  • a person who counts the delivery and confirms it;
  • payment terms from the shop, so Accounting knows when the bill is due.

S5 · The Yale AI Club accepts the quote and pays

Problem: the club accepts the $1,044 quote and pays a deposit.

Gap:

  • the replies were never sent, because there is no messaging tool;
  • there is no table for customer orders or sales;
  • no tool records money coming in to cash_accounts;
  • no tool reserves the 8 hoodies on hand.

Needed:

  • a send-message integration that runs only after a person approves the draft;
  • orders, sales, and reservation tables with tools that update them;
  • a customer-payment tool (or a payment processor integration);
  • a person who handles customer money.

S6 · October rent with $160 in checking

Problem: lease 1's next rent of $2,400 is due 2026-10-02, while checking holds $160 and $272 of purchase orders may soon be billed.

Gap: the team could find the shortfall (get_rent_due_and_cash, get_cash_balances) and prepare the payment, but the approval would be refused (no negative cash). There is no second account, no way to forecast incoming cash, and no rule for which bill to pay first.

Needed:

  • cash-flow data (expected sales and receivables) and a forecasting tool;
  • a bill-priority policy from the owner;
  • a person with financial authority, such as the owner or an accountant, to negotiate with the landlord or arrange funds.

Evidence gaps

  • Gap Whether PO 1 duplicates an earlier order. No field links invoice 501 ("Rush reprint CC-TEE-WHITE S") to PO 1.
  • Gap The vendor-blocking rule's origin. The rule that a vendor with an open invoice won't ship has been in harness.md since Problem 2, but its original source could not be re-confirmed, and no database field records it. The 101 and 103 behavior above depends on it.
  • Gap How much human time the process took. Human waiting time between runs was not measured, so the total time to resolve each ticket isn't reported.
  • Gap Why the agents chose their routes. The audit trail records what the agents did, not why they chose a route. Explanations of routing above are marked Inferred.
